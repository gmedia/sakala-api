## [Unreleased]

## [0.10.0] - 2026-11-20

### Added

- **Create a database for a project in one step.** `POST app/workspaces/{workspace}/databases` accepts `project_id` (uuid or `null`) and `deploy_when_ready` (boolean, default `false`, `422` without `project_id`). With a project, the database row, its `CreateDatabase` command, the attachment, the project's database fingerprint, and the audit events commit in one transaction under the workspace then project lock; this is the only way a `provisioning` database gets attached (the attach endpoint still refuses it). `name` becomes optional (the project's name, made unique with ` 2`, ` 3`, ... and cut to 100 characters), `region` defaults to the project's region then the workspace default, and an explicit other region answers `409 DATABASE_CROSS_REGION_UNSUPPORTED`. A project of another workspace answers `404`, a viewer `403`, a project that already has a database `409 PROJECT_DATABASE_ALREADY_ATTACHED`; quotas are unchanged. New `409 DATABASE_UNAVAILABLE` while `databases.available` is false, on this path only.
- **Deploy once the database is ready.** With `deploy_when_ready`, the request is kept on the attachment (new nullable `database_attachments.deploy_requested_by`, `deploy_requested_at`, `deploy_deployment_id`, `deploy_skipped_reason`, `deploy_resolved_at`). When the node reports `CreateDatabase` success, a queued job deploys the project through the normal deployment path as the requester with every limit (`trigger` `database_ready`, branch head, idempotency key `database-ready:{attachment}`), resolving the request exactly once. A failed or expired creation skips it with the new reason `database_provisioning_failed` and notifies the requester in-app (`project_issue`). Detaching removes the request. Audited as `database.project_deploy_requested`, `database.project_deploy_started`, and `database.project_deploy_skipped`. `ProjectResource.databases[]` gains `deploy_when_ready` (`null` or `status` `waiting`/`started`/`skipped`, `requested_at`, `deployment_id`, `skipped_reason`).
- Deployment `trigger` gains `database_ready`: the deployment the API starts once a database created with `deploy_when_ready` is ready, so the history no longer shows it as a manual deploy.
- Deploying a project whose attached database is `provisioning` or `failed` answers `409 DATABASE_NOT_READY` (`status`); push webhooks skip it with reason `database_not_ready`, audited and notified like `database_endpoint_unavailable`. Ready and locked databases are unaffected.
- **Env example and database hint from inspection.** `inspection` on `ProjectResource` and `CreateProjectResource` gains `env_example` (`file`, `entries` of `{key, example_value}`, `truncated`) and `database_hint` (`likely`, `engine`, `signals` of `{kind, file, name}`, `suggested_release_command`), from the agent's InspectProject result (revision 4, additive), stored in `projects.inspection`. Both are `null` for older agents and stored results. The API re-validates the agent's values on write and read: keys must be valid variable names (deduped, at most 200), example values are cut to 200 characters, at most 16 signals of known kinds, the engine from a fixed list, and the release command from a four-value allowlist; `likely` is recomputed.
- `ProjectResource.variable_changes` (always present; not on the project list or the create response): `requires_build` (true when any change to a project variable makes the next deployment build), `reason` (`static_site`, `prerender_framework`, `unknown_stack`, or `null` for a plain server), and `build_time_prefixes` / `build_time_keys` (the `BuildTimeVariable` lists, same order, matched case-sensitively), so the Console can say before a save whether the next redeploy builds. The OpenAPI enum `VariableBuildReason` also names `build_time_prefix`, the per-variable reason the Console shows for a plain server; it is never a project-level `reason`. See `docs/API_CONVENTIONS.md#variabel-yang-memengaruhi-build`.

### Changed

- **Static sites and prerendering frameworks build on any variable change.** `VariableBuildPolicy` classifies each project from its stored inspection (Railpack v0.23.0 signals, read with the same guard and labels as `stack`): a static site (`nodeIsSPA`, provider `staticfile`, `nodeRuntime` `static`, or a workspace `static_output_directory`, while the project has no start command) and a node framework that can render at build (`next`, `nuxt`, `remix`, `react-router`, `tanstack-start`, `astro`, `vite`, including SvelteKit) now treat every project variable as build-time, so a non-prefixed variable such as `API_URL` no longer serves a stale value from a reused image. So does a project without a usable inspection or with an unclassifiable stack (`shell`, unknown provider). Plain servers (Dockerfile builds, node/bun, php, golang, java, rust, ruby, elixir, python, deno, dotnet, gleam, cpp) keep the prefix rule. An attached database's connection variables never cause a build for any stack. Railpack reports Gatsby and Astro in server mode as plain `node`; see the frameworks entry below.
- **Frameworks from inspection count as build-time rendering.** The InspectProject result gains `frameworks` (agent protocol revision 4, additive): the build-time rendering frameworks named in the inspected `package.json` `dependencies` and `devDependencies`. The API re-validates it against the new enum `DetectedFramework` (`next`, `nuxt`, `astro`, `sveltekit`, `gatsby`, `remix`, `react-router`, `tanstack-start`, `eleventy`, `docusaurus`, `vitepress`; other values dropped, deduped, sorted) and stores it in `projects.inspection.frameworks` (`null` from older agents). `VariableBuildPolicy` checks it after the Dockerfile and static-site rules and before the Railpack framework rule: any value means `prerender_framework`, so Gatsby, Astro in server mode, Eleventy, Docusaurus, VitePress, and SvelteKit without a Vite config build on any variable change. `[]` or a missing field keeps the Railpack classification; a project inspected by an older agent moves only after a re-inspection, and then builds once. Not shown to the Console: `inspection`, `stack`, and `variable_changes` keep their shape.
- The build fingerprint of a plain server is byte-identical to v0.9.0, so live deployments keep matching. Static, prerendering, and unknown stacks hash every project variable under a new scope marker, so their first redeploy after this upgrade builds once (fail safe), as does a project whose re-inspection moves it to another class.

### Fixed

- `started_at` of an agent deployment is set by the agent's first accepted report (the moment its command turns `Running`) instead of its first phase status, and `deployment.updated` broadcasts it. A deployment that reused an image reports no phase until its container starts, so its duration left out the reuse and the release command (a staging reuse that took 37 seconds from creation to finish showed 20 seconds). Built deployments start a few events earlier than before, at the same point as reused ones.

## [0.9.0] - 2026-11-19

### Added

- **Redeploy without rebuild (image reuse).** A deployment of the live commit with no build-affecting change reuses the image of the project's active deployment instead of building again (`PlanDeploymentBuildAction`, the one place that decides): the active deployment may be serving, sleeping, or crashed, its stored build fingerprint must equal the new one, and the new deployment must be pinned to its node, which must advertise the new agent capability `image-reuse`. Build-affecting: `root_directory`, `build_command`, `start_command`, and build-time variables (keys starting with `NEXT_PUBLIC_`, `NUXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `VUE_APP_`, `GATSBY_`, `EXPO_PUBLIC_`, `PUBLIC_`, `RAILPACK_`, or exactly `NODE_ENV`); every other variable and the attached database's connection variables are runtime-only. The release command, health checks, replicas, zero-downtime switch, and active deployment and container limits apply as before. The auto-redeploy after a database password rotation now usually reuses the image, so apps reconnect without waiting for a build; so do redeploys after attaching or detaching a database or changing a runtime variable, and the manual Redeploy while the branch head is still the live commit. Deployments from before this release have no build fingerprint, so the first config redeploy after the upgrade builds once.
- `POST app/projects/{project}/deployments` accepts `force_build` (boolean, default `false`; other values `422`): `true` always builds ("Build ulang dari awal").
- `DeploymentResource.build` (always present): `mode` (`built` or `reused`), `image_source_deployment_id` and `image_source_sequence` (the deployment that built the reused image, `null` when reuse was never planned or that deployment was deleted), and `fallback_reason` (`image_missing`, `image_not_owned`, `image_metadata_missing`, `invalid_reference`, `image_unavailable` for any reason the API does not know; `null` unless reuse was planned and the agent built instead). The deployment list eager-loads the source, so it costs no query per row. See `docs/API_CONVENTIONS.md#redeploy-tanpa-build`.
- New `deployments` columns `build_mode` (default `built`), `image_source_deployment_id` (nullable FK to `deployments`, null on delete, indexed for that delete), `build_fallback_reason`, and `build_fingerprint` (HMAC-SHA256 with `APP_KEY`, hidden from serialization). Only defaulted or nullable columns; no backfill.
- Agent protocol revision 4, additive (`docs/AGENT_API.md#deployproject`): `DeployProject` gains the optional `reuse_image_from_deployment_id` (the deployment that built the image), sent only for a reuse plan to a node with `image-reuse`. The agent derives the image name and checks its labels itself. New events `deployment.image.reused` (no status change) and `deployment.image.reuse_skipped` (no status change; on a planned reuse it sets `build_mode` to `built` and `build_fallback_reason`, keeping the source). No new error codes.

- **Selective push deploys for monorepos.** A push now deploys only the auto-deploy projects it concerns: those with a changed file (the union of `added`, `removed`, and `modified` over `commits[]`) inside their `root_directory`, or with a changed file in no project's folder (a lockfile, a root README, `packages/...`). Folders are owned by every non-deleted project of the same workspace, repository, and branch, auto-deploy or not; a file belongs to the most specific root. A project without a root directory always deploys. Any doubt deploys as before: `forced` or `created` pushes, missing or empty `commits`, a push of only empty commits, 2048 commits (GitHub's cap), a commit with 3000 files (GitHub's per-commit cap) or without its file lists, a project that never deployed successfully, whose latest deployment failed, was cancelled, or is of another branch, or that had a push skipped for a limit since then. Manual deploys and other triggers are unchanged. No setting; watch paths are deferred.
- A push skipped that way is the audit event `project.push_skipped` (`github_app`, subject the project), written in the webhook's transaction, so a redelivery records nothing new. It is not a deployment: no sequence number, not counted against the build rate or active deployment limits, no metrics, no notification or email, and the project's latest deployment is unchanged.
- `GET app/projects/{project}/skipped-pushes` (`page`, `per_page` up to 100, default 20, optional `since`), for anyone who can view the project, lists those pushes newest first: `delivery_id`, `reason` (`no_changes_in_root_directory`), `commit_sha`, `commit_message`, `branch`, `root_directory`, `changed_path_count`, up to 5 `example_paths`, `after_deployment_id` (the newest deployment when the push arrived), and `created_at`. See `docs/API_CONVENTIONS.md#push-di-monorepo`.
- **Password rotation can redeploy attached projects.** `POST .../databases/{database}/rotate-password` accepts `redeploy_attached` (boolean, default `false`). Once the database node reports the new password, a queued job redeploys every attached project with a live deployment through the normal deployment path, as whoever asked for the rotation and with every limit: deployment `trigger` `database_password_rotated`, the live commit (the branch head if the project has moved to another branch), idempotent per rotation. A project that cannot be redeployed is skipped with a reason and keeps `redeploy_required`; the rotation still completes. Audited as `database.password_rotation_redeploys_queued`; `database.password_rotation_requested` gains `redeploy_attached`. The request and outcome live in the command's `request_context` and never reach the node.
- `GET app/pilot-limits` gains `databases.available` (boolean): true while at least one online node eligible for `CreateDatabase` (capability `managed-postgres`) last reported `metadata.database.available: true`. False on an installation without a database server, and while every database node is offline, drained, or its instance is down, so the Console can say databases are not offered here instead of offering a create that would wait or fail. Creating a database is not refused by it; existing databases stay listed. Computed per request from the same eligibility as placement, without a cache (one query over the nodes).
- `DatabaseResource.password_rotation` (`null` when never rotated): `status` (`pending`, `completed`, `failed`), `requested_at`, `completed_at`, `failed_at`, `redeploy_attached`, and `redeploys` (`null` until queued, then `project_id`, `deployment_id`, `skipped_reason` per attached project), so the Console can say when the new password is live and which redeploy to follow. The list eager-loads it, so it costs no query per database. See `docs/API_CONVENTIONS.md#rotasi-password`.
- `DatabaseResource.connection` (`host`, `port`, `database`, `username`, or `null` unless the database is `ready` or `locked` and its node reported an address) for everyone who can see the database, viewers included. The password and `DATABASE_URL` stay in the audited owner and admin `credentials` endpoint. The database list eager-loads the node, so it costs no query per database.
- `WorkspaceResource.default_region` (from the limit profile, `null` for any region) for every member, so the Console can name the region a database or project without one lands in.
- `GET app/projects` items gain `databases` (`id`, `name`, `status`), at most one per project, so the attach dialog can mark projects that already use a database.
- Agent failure code `runtime_app_host_blocked` (sakala-agent #112): the app answered, but Vite's preview or dev server or Django's debug page refuses the project's domain. Classified as user-fixable in category `start`; the hint names `preview.allowedHosts: ['.<project domain>']` (or `server.allowedHosts`), clearing the Start command so the build is served as a static site (with the package as Root directory in a monorepo), and Django's `ALLOWED_HOSTS`. The agent's message stays in `failure.detail`.
- `stack.monorepo` on `ProjectResource`, `CreateProjectResource`, and the project list: the `workspace` object of an `InspectProject` result (sakala-agent #113), stored in `projects.inspection.workspace`, with `manager`, `root_directory`, `package_directory`, `package_name`, `build_command`, `start_command`, and `static_output_directory`. `null` without a JavaScript workspace and for older agents; agent values that do not fit are dropped. The deployment event `deployment.workspace.detected` is kept on the timeline with that shape as metadata and changes no status (covered by a test, documented).
- **Email notifications for failed deployments and app problems.** A failed deployment, a crash of the running app, and a push that auto-deploy skipped are now also emailed (queued, after commit, in the shared mail layout) to the person behind it (the deployment's requester, or the account a push deploys as) while they are still an owner or member, and to every owner of the workspace; never to viewers, never to unverified addresses, and not at all when `sakala.email_delivery_enabled` is off. A successful deployment is emailed only to people who turn that on. The failure email names the project, deployment number, failed stage, the classifier's summary and recovery hint, and links to the deployment page in the Console; log lines and `failure.detail` never reach an email. In-app recipients are unchanged.
- `GET` and `PATCH app/notification-preferences` gain an `email` object with `deployment_success` (default `false`), `deployment_failure` and `project_issue` (default `true`), independent of the existing in-app booleans. `PATCH` accepts it partially, alone or together with in-app changes; other keys (such as `email.workspace`) or non-boolean values answer `422`. Stored in the new nullable `users.notification_email_preferences`; included in the account export.
- Repeated alerts are coalesced: at most one email per recipient, project, and kind of alert (`deployment_failed`, `deployment_succeeded`, `app_crashed`, `auto_deploy_skipped`) per `SAKALA_NOTIFICATION_EMAIL_COALESCE_MINUTES` (default 30, `0` sends every one); the next email says how many were held back. Tracked in the new `project_alert_mail_windows` table, unique on `(user_id, project_id, alert)` and claimed under a row lock.
- Every alert email carries a signed, non-expiring unsubscribe link and RFC 8058 `List-Unsubscribe` / `List-Unsubscribe-Post` headers. `POST api/v1/public/notifications/unsubscribe?category=&user=&signature=` turns off that category's email without a session (`403` on a bad signature, `422` for a category without email, `404` for a deleted account), rate limited per IP by `SAKALA_NOTIFICATION_UNSUBSCRIBE_RATE_LIMIT` (default 10 per minute). `GET` on the same address changes nothing and redirects to the Console page `/notifications/unsubscribe` with the same query, so link scanners cannot unsubscribe anyone.
- Five new mail previews: `project-deployment-failed`, `project-deployment-failed-repeated`, `project-deployment-succeeded`, `project-app-crashed`, `project-auto-deploy-skipped`. `SakalaMailMessage::preferences()` adds the footer links (notification settings, unsubscribe) and the one-click headers.
- **Managed PostgreSQL databases, phase 1 (part of #125, ADR-020).** A workspace-owned `databases` resource (model `ManagedDatabase`) hosted in the shared PostgreSQL instance of a database node, with random names on the node (`p_` and 20 lowercase letters and digits, different values for the database and its role, never reused), an encrypted 40-character password, `status` (`provisioning`, `ready`, `failed`, `deleting`, `locked`; `deleted` only on soft-deleted rows), `region`, `size_bytes`, and `size_checked_at`. New tables `databases` and `database_attachments`; new columns `agent_commands.database_id`, `projects.database_fingerprint`, `limit_profiles.max_databases`, `limit_profiles.max_database_storage_mb`, and `workspaces.database_storage_warned_at`.
- Endpoints under `api/v1/app/workspaces/{workspace}/databases`: list, create (`name`, optional `region`), show, rename, delete (`202`, then gone once the node drops it; refused while attached), attach and detach (`.../attachments/{project}`, same workspace only, one database per project), credentials (owners and admins only, audited before the password leaves, `Cache-Control: no-store`), rotate-password (`202`; the stored password changes when the node reports, while the node stops accepting the old one as soon as it runs the request), and extensions (`202`, one of `pgcrypto`, `citext`, `pg_trgm`, `unaccent`, `hstore`, `vector`). `DatabaseResource` carries `last_failure` (`command`, `code`, `user_fixable`, `summary`, `failed_at`) while the newest command for the database failed, with the agent's database error codes classified. Members manage databases like projects; viewers only read. New business errors: `DATABASE_LIMIT_EXCEEDED`, `DATABASE_STORAGE_LIMIT_EXCEEDED`, `DATABASE_REGION_UNAVAILABLE`, `DATABASE_CROSS_REGION_UNSUPPORTED`, `DATABASE_NOT_READY`, `DATABASE_LOCKED`, `DATABASE_IN_USE`, `DATABASE_BUSY`, `PROJECT_DATABASE_ALREADY_ATTACHED`, and `DATABASE_ENDPOINT_UNAVAILABLE`, all documented in OpenAPI.
- Attached projects receive `DATABASE_URL` (`postgresql://...?sslmode=require`), `DB_CONNECTION=pgsql`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, and `DB_PASSWORD` in the `DeployProject` environment, built at deployment time and never stored as project variables; a project variable with the same name wins. Attaching, detaching, and a completed rotation change the deploy fingerprint, so `redeploy_required` turns on. `ProjectResource` gains `databases` (`variables`, `overridden_variables`). The database password is redacted from deployment logs, command reports, and failure messages. Deploying without the database node's endpoint answers `409 DATABASE_ENDPOINT_UNAVAILABLE`; auto-deploy skips with reason `database_endpoint_unavailable`.
- Agent commands `CreateDatabase`, `DropDatabase`, `RotateDatabasePassword`, `LockDatabase`, `UnlockDatabase`, and `InstallDatabaseExtension` (revision 4, additive, capability `managed-postgres`, payloads as in sakala-agent PR #109), pinned to the database's node without a queue deadline, with the password encrypted at rest and decrypted only for that node. Their results move the database status; a lock turns the role NOLOGIN on the node, so backups keep running. Heartbeats may carry `metadata.database` (`endpoint {host, port}`, `available`) and `metadata.databases[]` (`{name, size_bytes}`, at most 1000, plus `metadata.detail_counts.databases`, only after a fresh reading); sizes update only databases of the reporting node, in one write, and a node whose instance is unavailable is chosen last for new databases. Contract: `docs/AGENT_API.md#perintah-database`.
- Limit profiles gain `max_databases` and `max_database_storage_mb`; `null` follows `SAKALA_DATABASE_DEFAULT_MAX_COUNT` (2) and `SAKALA_DATABASE_DEFAULT_MAX_STORAGE_MB` (512), and `0` allows none. `GET app/pilot-limits` gains `quotas.max_databases`, `current_databases_count`, `max_database_storage_mb`, and `current_database_storage_bytes`; the admin workspace quota shows the same.
- `databases:enforce-storage-quota`, every minute on one server: at 80 % of a workspace's storage quota its owners and members are notified once per crossing; at 100 % every ready database of the workspace gets `LockDatabase` and they are notified regardless of preference; below the quota, or after a raised quota, locked databases get `UnlockDatabase`.
- Deleting a project detaches its database, which survives. A team is deleted only once its databases are on their way out (`WORKSPACE_NOT_EMPTY` gains `databases`); deleting an account drops the databases of its personal workspace, and a sole owner of a team that still has databases gets `LAST_WORKSPACE_OWNER`. Every database mutation is audited.

### Changed

- The build rate limit (`max_builds_per_hour`, `SAKALA_PROJECT_MAX_BUILDS_PER_HOUR`) counts only deployments that build: a deployment planned to reuse the live image is not checked against it and does not count in the window. One that falls back to a build counts from then on, without being checked again. `BUILD_RATE_LIMIT_EXCEEDED.current` counts builds only.

## [0.8.0] - 2026-11-19

### Added

- **Basic per-project metrics (part of #128).** Heartbeats may carry `metadata.workloads.metrics` (agent revision 4, additive, from nodes with the new `workload-metrics` capability): one sample per replica with `project_id`, `deployment_id`, `replica`, `sampled_at`, `cpu_percent` (percent of one core, may exceed 100), `memory_bytes`, `memory_limit_bytes` (`null` for no limit), and `restart_count` (cumulative), plus `metadata.detail_counts.metrics`. At most 500 items; a malformed item rejects the heartbeat `422` like the other lists. Samples are kept only for a project's active deployment on the reporting node, the same rule as `traffic`; samples for other or unknown projects and deployments, and samples older than 10 minutes, are ignored without failing the heartbeat. The list is not copied into `agent_nodes.metadata`.
- Samples merge per replica per minute into `project_metric_minutes` (sample count, sum and maximum of CPU and memory, latest memory limit, highest restart count) with one upsert per heartbeat; a sample at or before the stored `last_sampled_at` of its minute is not counted again. `projects:roll-up-metrics`, scheduled every five minutes on one server, recomputes the previous and current hour into `project_metric_hours` (with restarts per hour, counter resets included) and prunes minute rows after `SAKALA_METRICS_MINUTE_RETENTION_HOURS` (default 24) and hourly rows after `SAKALA_METRICS_HOURLY_RETENTION_DAYS` (default 30). Both tables are indexed on `(project_id, bucket)` and cascade with their deployment. Row volume for 100 containers: about 144,000 minute rows and 72,000 hourly rows. See `docs/DATABASE.md#metrik-project`.
- `GET app/projects/{project}/metrics?range=1h|6h|24h|7d|30d` (default `1h`; same rights as viewing the project) answers `range`, `step_seconds`, and `series` with `cpu_percent` and `memory_bytes` (`{t, avg, max}`, summed across replicas), `memory_limit_bytes` (summed limit of the latest data, or `null`), `replicas` and `restarts` (`{t, count}`). 1h, 6h, and 24h read minute rows in 60, 300, and 900 second steps; 7d and 30d read hourly rows in 3600 and 14400 second steps. A step without data has no point, so gaps stay gaps; no data gives empty arrays. `per_replica=1` adds `series.per_replica`, the same series per replica index. See `docs/API_CONVENTIONS.md#metrik`.

## [0.7.0] - 2026-11-18

### Added

- **Build rate limit (#124).** `limit_profiles.max_builds_per_hour` is now enforced: a workspace may create that many deployments in a rolling 60 minutes. Every deployment counts, whatever its status, because every deployment builds a fresh image: manual deploys, redeploys, and push webhooks, failed and cancelled ones included, and deployments of deleted projects, so deleting and recreating a project does not reset the window. Wakes and restarts are not deployments and do not count. Over the limit, deploying answers `422 BUILD_RATE_LIMIT_EXCEEDED` with `limit`, `current`, and `retry_after_seconds` (when the window frees a slot, at least 1). The count runs under the workspace row lock, like the running container limit. Admins acting are not limited, and an idempotent replay still returns the existing deployment. Rejections are recorded as `rejected_limits` usage signals with `limit_name` `max_builds_per_hour`.
- `SAKALA_PROJECT_MAX_BUILDS_PER_HOUR` (default 20) is the limit for workspaces without a limit profile, personal and team alike, and for profiles whose `max_builds_per_hour` is `null`. Empty means the default; `0` turns the limit off.
- `GET app/pilot-limits` gains `quotas.max_builds_per_hour`, the effective limit (`null` means none).
- A push webhook over the build rate limit is skipped like the other limits: no deployment, a `project.auto_deploy_skipped` audit event with reason `build_rate_limit`, and a `project_issue` notification that says when to deploy again.
- `BUILD_RATE_LIMIT_EXCEEDED` is in the OpenAPI document of the deployment store endpoint, next to the validation error of the same status: responses that share a status with a business error body are now merged into one `anyOf` response instead of the last one winning.
- **Edge health monitoring.** Every authenticated `GET /api/edge/v1/routes` (200 or 304) records on the Edge token what the Edge reports: `User-Agent: sakala-edge/<version>`, `Sakala-Edge-Applied-Revision` (64 lowercase hex, or `none` before the first apply), and `Sakala-Edge-Status` (`ok` or a sakala-edge code, lowercase snake_case up to 64 characters). Missing or malformed headers are recorded as unknown and never fail the request. The row is written only when a reported value changes or the last write is older than 60 seconds. New `edge_tokens` columns: `last_version`, `last_applied_revision`, `last_status`, `status_since`, `revision_mismatch_since`, and `unhealthy_since`. The existing `last_used_at` is kept as the last-seen timestamp, not renamed, so API containers of the previous release keep serving the Edge during a rolling deploy.
- `php artisan edge:check-health`, scheduled every minute on one server, judges every Edge that is not revoked and was seen at least once. An Edge is unhealthy when it has not fetched the table (`stale`), reports a status other than `ok` (`status`), or serves a revision other than the current one, `none` included (`revision_behind`), for longer than `SAKALA_EDGE_STALE_AFTER_SECONDS` (default 300). An Edge that does not report its revision is judged on staleness only. Becoming unhealthy and recovering each write one audit event (`edge.unhealthy`, `edge.recovered`, actor `system`/`edge:check-health`, without token material) and email every admin once (`edge-unhealthy`, `edge-recovered`); a change of reasons while still unhealthy sends nothing.
- `GET api/v1/admin/edges` lists every Edge token ordered by name with `last_seen_at` (from `edge_tokens.last_used_at`), `last_version`, `applied_revision`, `current_revision`, `status`, `healthy` (`null` when revoked or never seen), `unhealthy_reasons`, `unhealthy_since`, and `revoked`, judged by the same rules as the command. Contract: `docs/EDGE_API.md#pemantauan`.
- **Per-project release command.** Projects gain `release_command` (nullable, one line without control characters, at most 1000 characters, like `start_command`), accepted by `POST` and `PATCH app/projects` and shown in `ProjectResource` and `CreateProjectResource`. It runs once per deployment before the new version takes traffic, for database migrations, and never on wake, restart, or reconcile. Changing it turns `redeploy_required` on; a project without one keeps its existing fingerprint.
- `DeployProject` payload `release_command` (agent revision 4, additive), only sent when set and only to nodes with the new `release-command` capability. When no node could run it (the project's node, or for a new project every active node), the deployment is refused up front with `409 PROJECT_RELEASE_COMMAND_UNSUPPORTED` instead of starting the new version without it; a capable node that is only offline is waited for. A waiting deployment follows its own payload, not later project changes. Auto-deploy skips such a project with `reason` `release_command_unsupported` and tells its owners and members.
- Failure codes `release_command_failed` and `release_command_timeout`, classified as user-fixable in the new failure category `release` (also accepted by the admin failure filter and counted in the failure summaries). The previous version keeps serving.

### Changed

- The admin workspace detail `quota.limits.max_builds_per_hour` is the effective limit (profile value, else the global setting; `null` means no limit) instead of the raw profile value. The limit profile resource keeps the raw value, where `null` follows the global setting.

### Fixed

- `redeploy_required` no longer turns on for every `PATCH app/projects/{project}`. A request without build fields or `replicas` used to mark the configuration changed whatever it changed, so renaming a project, or changing `thumbnail_url`, `auto_deploy`, or `region`, asked for a redeploy. The hint is now `true` only when the serving deployment was created with another deploy-relevant configuration: `branch`, the effective port (a port found by inspection counts while none is configured), `build_command`, `start_command`, `root_directory`, `replicas`, or environment variable keys and values. Changing a value back, or deleting a variable and adding it again with the same value, turns it off again; `is_secret` never counts. `branch` and a newly detected port, which were missed before, now count.
- Deployments store `config_fingerprint`, the deploy-relevant configuration they were created with, and projects store `environment_fingerprint`, an HMAC keyed with `APP_KEY` over their variables, recomputed under the project row lock by every variable change. Neither is exposed. Deployments created before this release keep the timestamp comparison until the next deployment, and a project gets its environment fingerprint at its next deployment, so no backfill is needed. Rotating `APP_KEY` shows one needless redeploy hint per project.

Running it again changes nothing.

A lowered profile maximum caps the next deployment without changing the project's setting.

### Added

Only nodes with the `idle-sleep` capability whose last heartbeat carried a traffic list take part, so a project never looks idle for lack of data. It is only sent to nodes with the `idle-sleep` capability; other nodes and idle sleeps keep receiving `{}`. Agent v0.7.0 ignores the field, v0.7.1 serves the page.

### Fixed

- A failed idle sleep is no longer asked again every minute. The sweep waits one idle window after the first failure in a row of the active deployment and doubles the wait with each further failure, up to 24 hours; a lifecycle command that succeeds on the deployment, or a new deployment, starts the count again. After `runtime_workload_not_found` it stops asking for that deployment until a new deployment or a wake or restart succeeds. On staging a container the agent could not see produced a failed command and an audit event every minute.

- Dependencies updated through Dependabot: the composer minor and patch group (14 packages), lint-staged, the nginx-unprivileged base image, actions/checkout v7, and docker/setup-buildx-action v4.
- The copy test now checks every Indonesian sentence in `app/` and `lang/id`, not only failure texts, exceptions, and notifications, so `project` and `Anda` cannot come back in validation messages or action errors.

## [0.2.1] - 2026-11-11

### Changed

- A `StopProject` created because a project is deleted (project delete, account deletion, an attempt that succeeds after the delete, and the daily retry of `projects:purge-deleted`) now carries `{ "remove_images": true }`, so an agent with that support also removes the project's images. Every other stop still sends `{}` and keeps the images. Agents up to v0.3.0 ignore the field.

## [0.2.0] - 2026-11-11

### Security

- The session cookie no longer reaches tenant applications. It is host-only on the API, with `SESSION_COOKIE=__Host-sakala-api-session` in production, and a `SESSION_DOMAIN` covering `SAKALA_PROJECT_DEFAULT_DOMAIN` is ignored. Only `XSRF-TOKEN` keeps a parent domain, through `SAKALA_XSRF_COOKIE_DOMAIN`. Existing sessions end and users log in again.
- `/broadcasting/auth`, which Laravel registers without CSRF checks, now accepts only origins in `SANCTUM_STATEFUL_DOMAINS` (`403 ORIGIN_NOT_ALLOWED`), so a tenant page cannot use the session there.
- Revealing a secret value is recorded in `audit_events` before the value is returned: actor, project, variable name, never the value.
- Agent failure messages are redacted before they are stored on the command and the deployment.
- Updated the Symfony packages with published advisories, and raised the `laravel/framework` minimum to `^13.30` so its vulnerable ranges cannot return.
- A project owner removed from a repository on GitHub can no longer deploy it: access is rechecked at deploy, webhook, and credential lease. Failure codes `repository_access_revoked` and `repository_access_check_failed`, and error code `REPOSITORY_ACCESS_REVOKED`.
- `POST auth/register` always answers 202 and no longer confirms whether an email exists; the existing account's owner gets an email instead.
- The exact values of a project's secret environment variables, and their common encodings, are redacted from stored and broadcast logs and events.

### Added

- Terms acceptance: `POST /api/v1/auth/register` requires `accept_terms`, `terms_version`, and `acceptable_use_version`; `POST /api/v1/auth/legal-acceptance` covers provider logins and new versions; `UserResource.legal_acceptance_required`; `GET /api/v1/auth/options` gains `legal`; `403 LEGAL_ACCEPTANCE_REQUIRED` on creating projects, inspection, and deploys.
- `DELETE /api/v1/auth/account` with re-authentication, which stops workloads, removes personal data at once, and leaves projects without an owner until their purge.
- `GET /api/v1/auth/account/export`, a bounded and rate-limited JSON copy without secret values or tokens.
- `suspension` (`{ reason, suspended_at }` or `null`) on `ProjectResource` and `GET /api/v1/app/projects`, so the owner can read why a project is suspended without parsing a notification. It is `null` unless the project is suspended, and the list reads it in one extra query.
- The owner of a suspended project gets the reason and the abuse contact, in-app and by email, regardless of notification preferences. `POST /api/v1/admin/projects/{project}/unsuspend` lifts a suspension.
- `sakala.email_delivery_enabled` (`SAKALA_EMAIL_DELIVERY_ENABLED`), which follows `mail.default` when unset, and `503 EMAIL_DELIVERY_UNAVAILABLE` on register, forgot-password, resend verification, and email change while it is off. Adding an SMTP provider needs env only.
- Public `GET /api/v1/auth/options` with `email_delivery_enabled` and `providers.github` / `providers.google`.
- `projects:purge-deleted`, run daily, permanently deletes a project `SAKALA_DELETED_PROJECT_RETENTION_DAYS` days (default 30) after its soft delete. Secrets go on time even while a node still has to stop the workload, and purged slugs stay reserved in `retired_project_slugs`.
- Sakala's own mail layout in `resources/views/vendor`: the product name instead of `APP_NAME`, a header that links to the console, and no framework salutation or footer.
- Laravel API-only control plane foundation.
- Sanctum, Socialite, Reverb, Sail, Pest, Pint, Larastan, and Scramble tooling.
- Versioned API status endpoint using Action, immutable DTO, and API Resource boundaries.
- OpenAPI 3.1 documentation UI, export command, analyzer, and access gate.
- Baseline security configuration and architecture tests.
- MVP database schema for users, OAuth accounts, projects, encrypted environment variables, deployments, agents, commands, events, logs, and audit history.
- UUIDv7 domain models, typed status enums, factories, and an idempotent local demo seeder.
- Database design documentation and persistence regression tests.
- `ProjectResource.active_deployment_id` and `effective_port`, and `DeploymentResource.is_active`, so the console can tell what is actually serving.
- `failure.detail`, `failure.stage`, and `failure.user_fixable` on deployments; detail and stage are stored on the deployment and survive log pruning.
- Agent failure codes `runtime_app_not_listening`, `runtime_app_unhealthy`, `runtime_app_crashed`, `runtime_app_out_of_memory`, and `runtime_port_conflict`.
- Optional heartbeat field `metadata.workloads.crashed_details` (protocol revision stays 4); it sets `runtime_status = crashed` for the active deployment and restores `running` when the crash is gone.
- Error code `PROJECT_SUSPENDED` and login error code `email_not_verified`.
- Indonesian validation messages in `lang/id`.

- Account security: change password, set a first password for OAuth accounts, change email through a signed link to the new address, forgot and reset password through the password broker. `UserResource` gains `has_password`, `pending_email`, and `created_at`.
- In-app notifications with per-category preferences, an unread count, broadcasts on `users.{id}`, and bounded retention.
- `order=desc` on `GET .../logs` with `per_page` up to 200, `log_sequence` on the `deployment.log.created` broadcast, and `Retry-After` in CORS exposed headers.
- `ProjectResource.serving_port`, the port the active deployment actually uses, stored as `deployments.container_port`.
- `ProjectResource.public_url`, from `SAKALA_PROJECT_URL_SCHEME` and `SAKALA_PROJECT_URL_PORT`.
- `public_url` and `latest_deployment` (`id`, `sequence`, `status`, `branch`, `commit_sha`, `commit_message`, `created_at`, `finished_at`, or `null`) on `GET /api/v1/app/projects`, and `latest_deployment` on `ProjectResource`. The list needs one extra query per page.
- `deleted_project_retention_days` on `GET /api/v1/app/pilot-limits`.
- Optional `GITHUB_PUBLIC_API_TOKEN`, cached public GitHub reads with ETag revalidation, and `503 GITHUB_RATE_LIMITED` with `Retry-After`.
- `SAKALA_AVATAR_STORAGE=local` for development, and `503 AVATAR_STORAGE_UNAVAILABLE`.
- `POST .../deployments/{deployment}/cancel`, `cancel_requested_at`, `queue_state`, and the additive `cancel_requested` field on `GET /commands`.
- Project build configuration (`configured_port`, `build_command`, `start_command`, `root_directory`), sent to the agent as optional `DeployProject` fields, and `redeploy_required`.
- `POST app/projects/{project}/inspection`, the derived `stack` summary, and the `90_days` project filter.
- `GET app/projects/domain-preview`, `search` on installation repositories, `DELETE app/profile/avatar`, and the `student` and `mentor` onboarding profiles.
- `PATCH .../environment-variables/{id}`; non-secret values are readable in the list.
- Opt-in `auto_deploy`: a verified GitHub push creates a deployment with the pushed commit, idempotent per delivery.

### Changed

- User-visible API messages, failure hints, and validation attributes now say `proyek` and `kamu`, and admin and GitHub errors that were still English are Indonesian. Codes and keys did not change.
- Deployment status follows `deployment.analysis.started`, `deployment.health.started`, and `deployment.route.started`. `health_checking` now ranks before `routing`, and `deployment.runtime.ready` no longer changes status. Older agents skip these statuses and still succeed.
- `InspectProject` sends `root_directory` when set, and `stack` is null until the current directory has been inspected. Added failure code `runtime_root_directory_invalid`.
- The default limit for authenticated API routes is 240 requests per minute (`SAKALA_API_RATE_LIMIT`); guests stay at 60 (`SAKALA_API_GUEST_RATE_LIMIT`).
- `REVERB_ALLOWED_ORIGINS` accepts URLs and normalises them to hostnames, which is what Reverb compares.
- Empty event `metadata` serialises as `{}` instead of `[]`, and empty usage signal `tags` likewise.
- A heartbeat leaves `runtime_status` alone while a newer deployment runs, and one crash sends one notification. `auto_deploy` is refused for public URL projects. Sail's default Reverb port is now 8080.
- `runtime_cancelled` ends a command as `Cancelled` and its deployment as `cancelled`, not failed.
- Deleting a project stops its workload through the agent, cancels queued work, and asks running attempts to stop.
- GitHub App installation returns to `/projects/new` with the result, and its failures redirect to the console instead of an API error page.
- A failed redeploy keeps the project `running` while the previous deployment still serves; `failed` now means nothing is live. The migration moves existing projects to this meaning.
- A successful restart or wake of the current workload sets `running`.
- Rewrote failure summaries and hints in Indonesian: each code says what to do, and platform faults say they are not the student's fault. `runtime_cancelled` moved from category `unknown` to `node`.
- Business rule errors now carry Indonesian messages; their `code` values did not change. The default locale is `id`.
- The owner of a suspended project now gets `409 PROJECT_SUSPENDED` when deploying instead of a generic `403`.
- Login with the right password on an unverified email returns `403 email_not_verified` instead of `401`.

### Fixed

- `api-web` resolves the `api` upstream through Docker's DNS while running, so recreating only the `api` container no longer leaves nginx answering 502 until it reloads.
- A correctly signed GitHub webhook whose `X-GitHub-Delivery` is not a UUID gets `422` instead of a 500 from PostgreSQL.
- A manual deployment of a commit whose first line is longer than 500 characters no longer gets a 500 from PostgreSQL. `commit_message` is now the first line without control characters, cut to 500 characters, for manual and push deployments alike; a push used to keep the whole multi-line message.
